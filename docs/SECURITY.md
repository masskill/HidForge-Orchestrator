# Безпека HidForge Orchestrator

## Принципи
1. **Жодних bypass-прапорців.** Адаптери ніколи не передають `--dangerously-skip-permissions`, `--yolo`, `--dangerously-bypass-approvals-and-sandbox`, `danger-full-access`, `--force`, `--trust`. Перевіряє тест `real adapters never emit permission-bypass flags`.
2. **Розділення режимів**: `read-only` (Claude `--permission-mode plan`, Codex `--sandbox read-only`, agy `--mode plan`, Cursor `--mode plan`) і `workspace-write` (Claude `acceptEdits`, Codex `workspace-write`, agy `accept-edits --sandbox`). Привілейовані дії (push, deploy, видалення, зміни secrets/глобального середовища) оркестратор не виконує взагалі.
3. **Без shell.** Усі процеси — `spawn(file, argv, { shell: false })`. Windows `.cmd`-шими розгортаються до `.exe`/`.js`; невідомий шим не запускається (захист від CVE-2024-27980 / ін'єкцій через cmd.exe).
4. **Немає довіри до результату агента**: незалежні gate-и після кожного запуску — git-коміт змін оркестратором, перевірка `allowedPaths` (включно з `..` та абсолютними шляхами), маркери конфліктів, команди перевірки. Merge — лише після ручного `Approve & Merge`.
5. **Команди перевірки** (`verifyCommands`):
   - жорсткий deny-list, який **неможливо** дозволити через UI: `git push/reset/clean/checkout/rebase…`, `rm/del/rd/format`, `powershell/pwsh/cmd/bash/sh/wsl`, `curl/wget/Invoke-WebRequest`, `npm publish/login/token`, усе з `deploy`, будь-які shell-оператори `| & ; < > \` $(`;
   - решта виконується **лише після явного дозволу користувача** для конкретного проєкту (`needs_user_input` → «Дозволити»); список зберігається в `projects.allowed_commands` і редагується в UI.
6. **Секрети**: HidForge не читає й не зберігає токени, ключі чи cookies провайдерів — використовується штатна авторизація CLI. `checkAuth` для Claude читає лише булеве `loggedIn` з `claude auth status` (вивід з e-mail не зберігається). Журнали, evidence і diff проходять через `maskSecrets` (ключі `sk-…`, `ghp_…`, `AKIA…`, `xox…`, `AIza…`, `Bearer …`, `api_key=…`, `password=…`).
7. **Локальний API**: слухає тільки `127.0.0.1`; перевірка заголовка `Host` (захист від DNS rebinding); усі не-GET запити, а також GET, що запускають процеси (`/api/diagnostics`, `/api/agents/:id/models`, `/api/agents?refresh=1`), вимагають `x-hidforge-token` (випадковий на кожен запуск, вбудовується в `index.html`), що змушує браузер робити CORS preflight, на який сервер не відповідає дозволом. Статика з CSP `default-src 'self'`. UI вставляє недовірений текст лише через `textContent`.
8. **Ізоляція записів**: окремий git worktree на задачу поза репозиторієм користувача; один writer на workspace — обмеження первинного ключа в БД.
9. **Завершення процесів**: `taskkill /PID <pid> /T /F` на Windows, kill групи процесів на POSIX; таймаут задачі й stall-таймаут (нема виводу N секунд).

## Модель загроз (скорочено)

| Загроза | Захист | Залишковий ризик |
|---|---|---|
| Prompt injection у README/коді змушує агента виконати шкідливу команду | Дозволи CLI не послаблюються; Claude headless відхиляє Bash без дозволу; Codex у sandbox | Залежить від sandbox-у конкретного CLI; agy `--sandbox` не перевірено щодо мережі |
| Агент пише поза дозволеними шляхами | Gate `allowedPaths` до merge | Агент **може** записати файл поза worktree на диск (якщо CLI дозволяє) — gate бачить лише git-зміни у worktree. Захист — дозволи самого CLI |
| Агент змінює `.gitignore`-файли (`.env`) | — | Gitignored-файли не потрапляють у diff і не мерджаться, але можуть бути змінені у worktree |
| Prompt injection у репозиторії спотворює план LLM-планера (зайві задачі, широкі шляхи, підозрілі команди) | Планер працює лише в read-only режимі CLI у тимчасовому detached worktree; план — лише пропозиція, задачі створюються після ручного «Додати як чернетки»; валідація шляхів і deny-list команд; кожна команда перевірки все одно потребує окремого дозволу | Людина має переглянути план перед застосуванням |
| Prompt injection у diff / коді задачі змушує AI-рецензента схвалити небезпечну зміну | Рецензент працює read-only в окремому тимчасовому detached worktree (зміни, якщо CLI їх таки зробить, відкидаються разом із worktree); prompt явно позначає diff і опис як дані й просить повідомляти про спроби ін'єкції; вердикт `approve` із `critical`-знахідкою знижується до `request_changes`; навіть `approve` не зливає зміни — фінальний `Approve & Merge` робить людина | AI-рецензія — додатковий фільтр, а не гарантія; режим `required` лише блокує, ніколи не зливає автоматично |
| Шкідлива веб-сторінка викликає локальний API | Host-перевірка + токен + відсутність CORS | — |
| Сторонній процес зупиняє сервер (`POST /api/shutdown`) | Як і всі не-GET запити — лише з токеном UI | Локальний процес з правами користувача може прочитати токен зі сторінки — модель загроз не захищає від шкідливого ПЗ на тій самій машині |
| JSON-плагін вмикає обхід дозволів або передає промпт в argv | Валідація при завантаженні: заборонені прапорці обходу, `{prompt}` в аргументах, шляхи в `bin`; вбудовані `id` зарезервовано; невалідний плагін не завантажується | Плагін — це команда, яку HidForge запускає від імені користувача: класти в теку плагінів лише специфікації, яким довіряєте |
| Запуск агента у WSL | `wsl.exe --exec` без shell, назва дистрибутива — лише `[\w.-]`, промпт через stdin | Експериментально; агент у WSL має доступ до всіх `/mnt/<диск>` — обмеження — лише дозволи самого CLI |
| Запуск агента на VPS через SSH | Лише ключ/агент користувача (`BatchMode=yes`, без паролів), known_hosts не вимикається; хост і тека — суворі шаблони (не можуть стати опцією ssh чи кодом shell), решта слів у одинарних лапках; на хост не йдуть `.git`, ігноровані файли (`.env`) і symlink; патч назад без symlink і `.git`, далі звичайні gate-и | Експериментально; код проєкту **виходить на ваш сервер** — вмикайте лише для своїх хостів; скасування не гарантує зупинку віддаленого процесу |
| Оновлення перезаписує локальні зміни або тягне довільну гілку | `update.ps1`: лише `merge --ff-only` з origin поточної гілки, відмова за наявності змін у відстежуваних файлах, `-Check` без змін | Довіра до origin-репозиторію |
| Інсталятор змінює систему без згоди | Лише ярлики користувача (робочий стіл, «Пуск»), без прав адміністратора й без встановлення залежностей; `-Uninstall` прибирає ярлики | — |
| Ін'єкція аргументів на Windows | Без shell, розгортання шимів, тест `spawnSafe passes tricky arguments verbatim` | — |
| Перевикористання PID після перезавантаження ОС → вбивство чужого процесу при відновленні | Kill лише якщо запуск молодший за свій таймаут | Мала ймовірність; позначено `ponytail:` у коді |
| Витік секретів у журналах | `maskSecrets` | Евристика; нестандартні формати секретів не маскуються |

## Відомі обмеження
- Codex на Windows: якість sandbox-у `workspace-write` залежить від версії Codex.
- Cursor headless працює лише в «довіреному» каталозі. HidForge передає `--trust` тільки після явного ввімкнення користувачем у Налаштуваннях (налаштування `agentTrust`, типово вимкнено); `--force`/`--yolo` не передаються ніколи.
- Немає автентифікації користувачів — розраховано на одного локального користувача.

**Назви моделей.** Модель передається CLI окремим аргументом після `--model`, тому значення валідуються на вході (задача, планер, рецензент): лише `A–Z a–z 0–9 . _ : / @ [ ] , = + -`, без `-` на початку. Так значення на кшталт `--dangerously-skip-permissions` не може стати прапорцем CLI.
